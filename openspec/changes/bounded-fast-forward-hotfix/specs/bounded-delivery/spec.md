# Bounded delivery

## ADDED Requirements

### Requirement: Current bounded admission

The host SHALL admit an unattended request only under authenticated owner intent and current project policy, preserving canonical lifecycle gates and human-only decisions.

#### Scenario: Default fast-forward eligibility

- **GIVEN** current bounded authority and an explained low-risk reversible issue estimated at 1, 2 or 3 points
- **WHEN** refinement and independent plan review satisfy their evidence
- **THEN** delivery continues without routine human acknowledgements
- **AND** five-point work requires explicit adopter opt-in

#### Scenario: Human attention or changed authority

- **GIVEN** a pending owner answer/review, revoked reservation, changed source/policy or ambiguous product meaning
- **WHEN** admission or continuation is evaluated
- **THEN** dependent advancement stops with an actionable outcome

### Requirement: Independent engineering review

The host SHALL execute a separate read-only reviewer using a distinct configured model and bind its verdict to the current candidate, criteria and executed evidence.

#### Scenario: Incorrect candidate with a weak passing test

- **GIVEN** a candidate that passes its supplied test while violating acceptance
- **WHEN** independent review inspects original intent and actual before/after source
- **THEN** the candidate is rejected or escalated and cannot integrate

#### Scenario: Bounded corrections

- **GIVEN** a concrete bounded correction and remaining repair budget
- **WHEN** the implementation is revised
- **THEN** affected checks and independent review are repeated
- **AND** exhausted budget, stale verdict or unavailable proof stops publication or integration

### Requirement: Test-first hotfix evidence

The host SHALL require a meaningful RED behavioral assertion against unchanged production code, preserve the regression-test bytes through repair, and require GREEN and applicable checks before integration.

#### Scenario: Isolated boundary defect

- **GIVEN** a confirmed root cause, trusted regression command, rollback context and a planned bounded correction
- **WHEN** the regression fails before production repair and passes afterward
- **THEN** independent review receives RED, GREEN, test snapshots and actual scope
- **AND** the complete candidate is limited to 100 production additions plus deletions, 10 files including tests and two declared modules

#### Scenario: Invalid proof or scope overflow

- **GIVEN** an environment failure, altered regression assertion, unassessed binary change or exceeded scope limit
- **WHEN** host verification runs
- **THEN** unattended hotfix stops and preserves the candidate for inspection

### Requirement: Separately authorized integration

The host SHALL publish a verified candidate and merge it only under separate current bounded delegation and satisfied hosting requirements.

#### Scenario: Delegated merge

- **GIVEN** current independent acceptance, passing required CI and explicit merge policy
- **WHEN** the final head, base, scope, policy and review are rechecked
- **THEN** integration records the actual merged revision and retained evidence
- **AND** existing post-merge review and protected release/deployment decisions remain separate

#### Scenario: Duplicate or uncertain effects

- **GIVEN** a replayed request or uncertain publication/integration
- **WHEN** a later execution inspects its retained identity
- **THEN** it stops for reconciliation instead of repeating the effect
