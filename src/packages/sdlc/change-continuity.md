# Change context and instruction review

Before proposing or continuing a change, use `context.continuity` to locate the admitted work item, task digest, source revision, decision owner and original inputs. The full intent and criteria remain in `context.issue`; questions and decisions remain in its owner answers and the retained predecessor evidence. Read those original records. The context contains pointers and provenance instead of a second product definition. Imported observations and task text do not establish approval. ProductShape owns product meaning; ArcShape owns architecture; the trusted host authenticates execution and decisions.

The host rechecks the original title, body and owner-answer identities, contents and revisions before continuation/publication. A changed task digest requires fresh refinement under the named owner. Preserve the old record and the new decision; a worker cannot reinterpret the old grant to cover changed intent. Conflicting product, architecture or instruction authority requires a blocked result naming both sources and the responsible owner.

At implementation completion, when `request.instructionReview` is `1`, return `output.instructionReview` using `contract.instructionReview`. Inspect the guidance reached by the changed behavior: applicable `AGENTS.md`, its pointers, selected skills, workflow prompts and affected package or architecture guidance. Record each inspected repository path, owning project/tool, disposition and concrete supporting evidence. Use `reviewed` with source findings, or `not-applicable` with a bounded reason and no sources. A source can be `current`, `corrected` or an intentional `host-specific` projection. Distinct host commands or paths are legitimate when they preserve the canonical policy; explain the owning contract instead of normalizing every host.

Report `stale`, `conflict` or `missing` sources as `blocked` with the decision owner and next action. A passed completion cannot retain those findings or refer to a source absent from the candidate. These checks validate the report and its paths; semantic consistency still requires the worker's inspection and independent review. Syntax validation alone does not prove that prose agrees with implementation.

Keep shared instructions in their canonical package source and host projections thin. Regenerate provider-owned projections through the pinned provider and verify drift. Repair project-owned guidance in the reviewable candidate. Preserve historical ADR decisions and qualify their later implementation status with current source evidence. Unrelated guidance does not require a rewrite, and this review creates no new lifecycle stage or approval authority.
