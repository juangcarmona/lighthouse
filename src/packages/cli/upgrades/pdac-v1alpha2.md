# Adopt PDaC v1alpha2

Every Lighthouse adopter, including Lighthouse itself, requires explicit PDaC `v1alpha2` configuration and a compatible ProductShape provider. Lighthouse currently pins `@prodshape/cli@0.26.1` and `@prodshape/core@0.25.0`; both support this contract. Package versions and PDaC serialization are independent. Upgrading a package or changing only the version declaration does not complete migration.

## New product authority

Install the selected Lighthouse package, review `lighthouse authorities --dry-run`, then run `lighthouse authorities --apply`. The ProductShape plan explicitly selects `prodshape --serialization-version v1alpha2 init --full --sdd none --gitignore`. Initialization creates provider-owned authoring surfaces; empty or draft content is not approved product intent. Run `lighthouse verify` after authoring and validating the required authority.

A scaffold with no explicit product configuration remains an incomplete adoption, even with the public documentation site disabled. Verification reports a required `foundation.pdac` failure. Initialization and reconciliation can prepare Lighthouse-owned files while reporting that adoption gap; this permits repairing the harness before completing product migration. Upgrade plans report product gaps as pending adoption and do not mutate provider files.

## Existing model

1. Commit or isolate the current repository. Record the source revision, ProductShape version, serialization version, model inventory, active Product Changes, consumer citations and existing test evidence. Run `prodshape validate` and `prodshape change validate` against the current contract. Repair existing errors before migration.
2. Review the installed v1alpha2 schemas with `prodshape --serialization-version v1alpha2 schema business-rule`, `schema use-case`, `schema constraint`, `schema domain-lifecycle` and `schema structured-behaviour`. ProductShape remains the format authority. Its current CLI has no serialization-migration command; do not substitute its filename/ID fixes or overwrite existing content with an initializer.
3. Prepare the conversion in an isolated copy. Use the supported `@prodshape/core` parser and repository APIs for provider artifacts. Preserve stable IDs, body text, artifact status and existing product meaning. Move each use-case selector from a business rule's `applies-to` into that use case's `governed-by`, retaining existing rule links and deduplicating them. Preserve journey and bounded-context selectors. Check the resulting governance pairs against the original selector pairs so no rule is lost. Review empty scope selectors explicitly; do not invent a wider scope to satisfy validation.
4. Review constraints and other changed relationship/scope semantics against the provider schemas. If the conversion needs a new product decision, draft a Product Change and obtain its human approval before provider apply. A mechanical representation migration grants no approval of unrelated product proposals.
5. Inspect active Product Changes under the target contract, including their complete proposed artifacts. Convert representation where necessary and revalidate every overlay without changing proposal status or accepting its meaning. Keep archived changes and historical evidence as historical records; their old digests can legitimately become stale.
6. Set `.product/config.yaml` to `version: v1alpha2` in the isolated conversion, then run `prodshape --serialization-version v1alpha2 validate` and `prodshape change validate`. Any blocking diagnostic prevents recording compliant adoption. Capture the original bytes of every migrated file and restore them if application or validation fails.
7. Classify affected citations through supported ProductShape citation verification. For current consumers, reread the claim against the new model, revise it when necessary, and obtain fresh `inspect`/`cite` payloads. Preserve historical test documents, outcomes and original revisions; report stale applicability and create new runs for revalidation. See the SDLC package's `product-verification.md` for scenario derivation and external evidence verification.
8. Review the diff and migration evidence, then run `lighthouse authorities --adopt-existing --format json`. Resolve product and architecture validation conditions, review the dry run, and use `--apply` to record exact provider versions in Lighthouse-owned configuration and regenerate its projection. The serialization version stays explicit in provider configuration and appears separately in Lighthouse reports. Run `lighthouse verify --format json` and the adopter's domain, integration and applicable E2E checks.

Restore the pre-migration commit and its ownership metadata if verification fails; keep the failed validation and test receipts. Never reinitialize a populated model as a repair shortcut. Lighthouse's adoption operation leaves provider content untouched.

Missing configuration, v1alpha1, conflicting version declarations and unsupported providers are adoption gaps with repair routes in text and JSON. A deferred migration remains pending; it cannot become compliant through an omitted integration, selected profile or successful harness update.
