# OpenCode engine on a single Linux host

Use a dedicated self-hosted Actions runner with the `lighthouse-workflow` label. GitHub queues jobs; each invocation starts one temporary Docker container. No Lighthouse daemon, database or SoFa service is required. Register repository runners according to your account's scope and restrict them to trusted workflows.

Build with `bash src/examples/opencode-engine/build.sh /absolute/path/to/opencode` using OpenCode 2.1.0. The script builds a read-only tool profile and a separate `lighthouse-engine:2.1.0-implement` profile with shell/edit permissions baked into system policy. Pin both image IDs; `implementationImage` is required only for implementation. Pin the read-only image ID from `docker image inspect lighthouse-engine:2.1.0 --format '{{.Id}}'`. Authorize OpenCode separately in an operator-owned Docker volume; do not put credentials in Git or in the configuration below.

For repository-selected base and .NET build environments, use the [pinned-input environment builder](ENVIRONMENTS.md) instead of the legacy implementation image recipe. It adds preflight checks and optional temporary PostgreSQL while preserving the existing read-only image and undeclared consumers.

The host also preflights legacy images before model execution. Required image executables must already be installed; a project-local tool is checked in the candidate after its dependencies are installed. Engine and independent checks use `/tmp` for scratch/npm/XDG caches with Node compile caching disabled. Keep only final logs, command receipts and reports in `/output/evidence/`. Collection runs after workload exit and recovers ownership only inside that execution's temporary tree; shared authentication volumes and other runs are outside it.

The included `Dockerfile.runner` supplies Node, GitHub CLI, Docker CLI and Linux runtime dependencies. Build it with `docker build -f src/examples/opencode-engine/Dockerfile.runner -t lighthouse-runner:gh-aw .`. Register the Actions runner in an operator-owned directory, then mount that directory into the runner container **at the same absolute path as on the host**. Its work directory must also be beneath this mount: sibling engine containers resolve bind mounts through the host Docker daemon. Give the runner its own `HOME` and `/tmp`, the host Docker socket and the socket's group; run it as the directory's non-root owner. On Linux, run the runner container with `--network host`: gh-aw starts its authenticated MCP gateway on host port 8080 and the runner must reach it through localhost. Reserve that port and allow only one gh-aw agent job on this host at a time; the engine lock covers model execution, not gateway startup. Start the image in the registered runner directory. Its entrypoint uses Tini to reap orphaned descendants and wraps `run.sh` with the packaged telemetry producer; mount a persistent private `LIGHTHOUSE_TELEMETRY_DIR` and preserve any existing job hooks. See the [telemetry setup and consumption contract](../../packages/sdlc/telemetry.md). Never mount the operator's normal home directory.

Rebuild the runner image and recreate idle runner containers to adopt its entrypoint. Updating the SDLC package alone does not replace a running container. Execution-owned container removal also deletes its anonymous volumes, including during phase cleanup; named authentication and shared volumes persist. Previously orphaned volumes require separate inspection because the removed container can no longer establish their execution ownership.

For multiple repository runners sharing this host, install [the job-start hook](job-start.sh) through `ACTIONS_RUNNER_HOOK_JOB_STARTED`. Set `LIGHTHOUSE_HOST_GATEWAY_LOCK` to the same absolute lock file on every runner, with its parent directory mounted at the same host path. The hook holds that gateway slot for the whole Actions job, releases it when the worker exits, and reports elapsed queue time. Its default wait is 1,800 seconds; set `LIGHTHOUSE_HOST_SLOT_WAIT_SECONDS=7200` only after adopting workflows with the 180-minute agent job budget. The existing 30/55-minute execution-step limits and adapter resource limits stay unchanged. This permits up to two hours of host waiting plus execution and teardown; it does not add parallel model capacity. Native unattended delivery skips the gateway slot and retains its own engine admission.

Use a disk-backed operator scratch directory for manual checkouts and test fixtures when the host `/tmp` is a small tmpfs. Check both available bytes and inodes before installing dependencies. Keep manifests and source when retiring generated dependency trees; execution cleanup cannot claim ownership of a manually created checkout.

Set `LIGHTHOUSE_ENGINE_CONFIG` in the runner service environment to a private JSON file:

```json
{
  "image": "sha256:<64 lowercase hexadecimal characters>",
  "implementationImage": "sha256:<64 lowercase hexadecimal characters>",
  "uid": 20003,
  "authVolume": "lighthouse-engine-auth",
  "model": "openai/gpt-6.1-sol",
  "lock": "/absolute/operator/state/engine.lock"
}
```

To offer the operator's installed CodeGraph binary to read-only workers, add `"codegraph": { "enabled": true, "binary": "/absolute/path/to/codegraph-server" }` to that JSON. Each run starts a disposable CodeGraph container against its tracked-file snapshot with a private index, no network or credential mount, and only `codegraph_symbol_search` and `codegraph_get_ai_context` exposed. The host checks that OpenCode connects before admitting the capability. `runtime.json` reports `available`, `unavailable` or `disabled`; a missing binary or failed connection leaves normal file tools usable. Set `enabled` to `false` or remove the entry to disable it. Editable implementation workers do not use CodeGraph because their source can change after indexing. Keep the binary and its indexes under operator ownership; do not add either to the repository.

Create the lock's parent directory and a private `<lock path>.resources` directory before starting the runner. Mount the resources directory persistently at that same absolute path for containerized runners; mounting only the lock file is insufficient. Every runner on this physical host must use the same lock and journal paths. The standard Linux `flock` serializes engines and releases capacity when the adapter process exits. Waiting longer than four minutes fails visibly; refine/propose have ten minutes to finish. Implementation has thirty minutes plus ten minutes for independent checks. Docker limits it to two CPUs, 2 GiB memory and 128 processes. Cancellation removes its container, and normal cleanup deletes its OpenCode session. [Cleanup evidence and restart admission](../../packages/sdlc/execution-environments.md#execution-and-isolation) remain separate from execution success and retry authority.

The adapter mounts tracked regular source files read-only, excludes `.git`, untracked files and symlinks, and bounds the snapshot to 5,000 files and 32 MiB. It mounts the pinned harness package read-only at `/harness`, with skills discovered by OpenCode. Refine/propose can write only their result through the configured tools. Implementation selects a separate policy that allows shell execution and edits in a disposable source copy; the adapter enforces publication scope independently. Its agent and validation containers default to 4 GiB memory and 1,024 process/thread slots, and the image includes Chromium for browser checks. Its validation container receives the candidate and public networking, without the provider volume or GitHub credentials. The provider volume persists authentication; session cleanup does not claim to erase all provider logs or cache.

The runner owns Docker access and can control the host. The agent container receives neither that socket nor GitHub credentials. This subscription profile does not use AWF network filtering or an external credential proxy: outbound networking is available and provider authentication lives inside the engine container. Use a separate host for mutually untrusted workloads. Additional parallel capacity requires separate authentication/workspace handling and isolation review.

Install the package's selected gh-aw workflows, review their immutable implementation pin, then enable `LIGHTHOUSE_AUTOMATION_ENABLED` on the consuming repository. Stop any older router/executor only after its active run has finished. Opt in to proposal delivery with `--with-propose`, or proposal and implementation with `--with-implement`. Rebuild and repin this image before enabling implementation. OpenSpec runs in the hosted preparation and publication jobs; the engine image needs no provider installation. Follow `refine / agent`, `propose / agent` or `implement / agent` → `OpenCode progress and result` for public progress messages, concise tool activity and the validated result. During quiet intervals the step reports elapsed time without claiming new progress. The result also appears in the job summary. The separate `opencode-events` artifact keeps the redacted structured stream used by gh-aw to build session and usage evidence. Preparation and conclusion jobs are framework infrastructure; the host keeps no competing lifecycle database.

Implementation uses the V2 `shell` permission, distinct from the V1 `bash` name; see the [OpenCode V2 permission reference](https://opencode.ai/v2/docs/permissions). Its configured shell can execute repository code with the engine container’s authority, including access to provider authentication. It is unsuitable for mutually untrusted workloads. The separate candidate checks have no provider credential mount.

The adapter keeps complete diagnostic lines up to 8,388,608 characters. It records an explicit omission for larger events and continues execution; it never publishes a partial log line. Candidate source is collected independently. Failed implementation runs retain bounded in-scope changes and available evidence where possible, but cannot publish a PR or emit a successful completion. npm uses a temporary writable cache. gh-aw completion remains a host duty, so the engine does not need the `safeoutputs` CLI.

Engine and validation containers use Docker’s init process to reap orphaned browser children after interrupted checks. Keep browser concurrency within the configured CPU, memory and process limits.

## Provider transport

Both example policies select HTTP streaming for OpenAI through `providers.openai.settings.transport`. A provider WebSocket closure can leave OpenCode with a nonzero exit status even after subsequent steps finish. HTTP avoids that connection-reuse path while preserving the model, authentication and permissions. See the [OpenCode transport settings](https://opencode.ai/v2/docs/providers/#websockets).

Rebuild the affected engine images and update their immutable operator pins between executions. Provider errors still fail the worker; a completed model message does not replace a successful engine exit, independent checks or required review.

After an atomic replacement of the operator configuration, restart idle runners that bind-mount that file so they read the new inode. Runners mounting its parent directory see the replacement directly. Verify the configured image from inside each runner before admitting work.

## Browser resources and command completion

See the packaged [resource and command-completion contract](../../packages/sdlc/execution-environments.md#resource-limits-and-command-completion) for operator settings, command receipts and failure diagnostics. Update each adopter through the [workflow installer](../../packages/sdlc/README.md#install-or-update-workflows), validate one consumer and then roll out between runs. Adapter and mounted-skill updates require a new immutable workflow pin; an engine-image rebuild is needed only when its tools, binary or baked policy change.
