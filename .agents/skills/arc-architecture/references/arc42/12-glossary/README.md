# 12. Glossary

**Purpose.** Define domain and technical terms stakeholders use so architecture discussions have consistent meanings and avoid ambiguous synonyms or homonyms.

## Subsections

- **Term/definition table; optional translations or model links.** Use it when the project has relevant information; preserve project-specific naming or grouping.

## Evidence to examine

- Product vocabulary, domain models, API schemas, identifiers, and stakeholder terminology.
- Existing glossaries, terminology services, translations, and naming conventions.

Use these as investigation leads, not automatic proof. Prefer current implementation, tests, configuration, and maintainer-confirmed decisions appropriate to the claim. Cite concrete repository evidence in resulting documentation. Separate observed behavior, accepted intent, inference, and proposal.

## Gaps and conflicts

- If evidence does not establish useful content, state what is missing and ask the maintainer for context.
- If sources disagree, describe the competing evidence and its source; do not silently choose one. Ask the maintainer to resolve intent or status.
- Do not invent names, responsibilities, boundaries, measures, owners, dates, or rationales to make the section appear complete.
- If the project omits, combines, or adapts this section, follow that choice and link to the content location when known.

## Practical guidance

- Define terms in the system’s context and identify ambiguous synonyms or homonyms.
- Do not choose between conflicting meanings without evidence or maintainer direction.
- Keep the glossary useful and compact; link an authoritative glossary when one exists.
- Include translations only when the project needs them.
